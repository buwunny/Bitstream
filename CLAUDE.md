# BITSTREAM.sh: notes for contributors and agents

BITSTREAM.sh is an open-core FPGA toolkit: a Rust core (this Cargo workspace)
behind a thin VS Code extension (later milestone). See `README.md` for the user
view and `ROADMAP.md` for what comes next. Milestone 1 covers only manifest, board
data, rule checks and constraint generation. Don't start later milestones unless
asked.

## Layout

| path | what |
|------|------|
| `crates/manifest` | `bitstream.toml` schema (serde + `toml::Spanned`), structural validation, and the shared `Diagnostic` type with its rustc-style renderer |
| `crates/boards` | data model and loader for `boards/**/*.toml`; `build.rs` embeds every data file |
| `crates/rules` | resolves `[pins]` to package pins (`resolve`) and runs board-level checks (`checks`) |
| `crates/constraints` | XDC (Vivado) and PCF (nextpnr-ice40) generators |
| `crates/cli` | the `bitstream` binary (clap): `init`, `check`, `constraints`, `build`, `sim` |
| `boards/` | family, device (package pinout) and board data, see `boards/README.md` |
| `scripts/` | stdlib-only Python generators for device files from vendor pinouts |
| `examples/` | example projects, also used as golden-test inputs |
| `docs/manifest.md` | manifest reference |
| `crates/lsp`, `extension/` | later milestones (not created yet) |

Data flow: `Manifest::parse` → `bitstream_rules::check(&manifest, Database::builtin())`
→ `Report { target, ports, diagnostics }` → `bitstream_constraints::generate`.

## Conventions

- **Board data is data.** Pins, banks, voltages and IO standards live in
  `boards/*.toml`, never in Rust code. Every value comes from a primary source
  (AMD/Lattice pinout files and user guides, the board vendor's master constraint
  file, reference manual or schematic, or LiteX platform files), and the URL is
  recorded in the file. Never invent pin data: leave unverified values out and
  add a TODO. Device files are generated by `scripts/`; regenerate them, don't
  hand-edit.
- **Diagnostics.** Every user-facing problem is a `Diagnostic` with a stable
  kebab-case `code` (`bank-voltage`, `diff-pair`, …), a primary span into the
  manifest, and a `help` line when there's an obvious fix. Rules are pure
  functions `fn(&[ResolvedPort], Target) -> Vec<Diagnostic>` in
  `crates/rules/src/checks.rs`.
- **Determinism.** Generated constraint files must be identical byte for byte
  across runs and platforms: sorted output, `\n` line endings, no timestamps,
  paths or versions. Golden files live in `crates/constraints/tests/golden/`;
  regenerate them with `UPDATE_GOLDEN=1 cargo test -p bitstream-constraints`
  and review the diff.
- **Tests.** Each rule check has at least one passing and one failing manifest,
  tested against real board data. Prefer small inline manifests in tests.
- **Vendor and GPL tools.** Never bundle or host vendor tools (Vivado, Quartus).
  GPL tools (Verilator, Icarus, NVC, GHDL) run only as separate processes, never
  linked in.
- **Dependencies.** Stick to common, well-maintained crates (serde, toml, clap,
  thiserror). Ask before adding anything else.
- **Before every commit:** `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
  CI runs the same three.
- Timing constraints are not modeled: native XDC/SDC files listed in
  `[constraints] files` pass through unchanged.
